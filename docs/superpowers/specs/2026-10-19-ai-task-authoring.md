# AI-авторинг задач: курс/задача по описанию человека через агента

Дата: 2026-10-19
Статус: задача поставлена, реализация не начата
Область: MCP-инструменты (авторинг + harness), backend (draft-run без посылок), опционально AI Assist UI
Предварительно полезно: спека `2026-10-19-task-search.md` (поиск задач → дедупликация аналогов)

## Суть

Человек описывает задачу на человеческом языке — например, ту, что видел на
интервью — и просит агента создать её в CourseForge: целиком новый курс или
задачу в существующий курс, в нужное место иерархии
(Catalog → Course → Track → Topic → Unit).

Агент при помощи AI:

1. разбирает описание, находит курс/топик, куда задача ложится,
   проверяет, нет ли уже аналогов во всей библиотеке;
2. задаёт уточняющие вопросы **обязательно** — corner-кейсы, ограничения,
   нестандартные условия, расширения задачи («а если вход пустой?», «числа
   всегда положительные?», «нужен ли стабильный порядок?»);
3. пишет эталонное решение, шаблоны и тесты, покрывающие все corner-каналы;
4. прогоняет решение через тест-харнесс в цикле «запустил → увидел падение →
   исправил → запустил» до полного зелёного, **не создавая посылок и не
   трогая прогресс**;
5. по подтверждению пользователя записывает файлы задачи на диск и
   перерегистрирует курс.

Рабочие поверхности: через MCP (агент IDE/CLI) — основной путь; встраивание
этого потока в AI Assist UI — опционально позже, механика та же.

## Диалоговый протокол (что агент обязан сделать)

1. **Понимание и дедупликация.** Распарсить описание, найти кандидатов:
   `search_tasks` (см. спеку поиска) или `list_courses`. Если нашлись
   похожие задачи — показать их человеку и спросить: «новая или вариация?»,
   в каком курсе/топике разместить.
2. **Уточняющие вопросы — обязательный шаг.** Переходить к генерации можно
   только когда закрыт чек-лист:
   - ограничения входа (диапазоны, пустой ввод, дубликаты,负 отрицательные);
   - формат ввода/вывода (строки/массивы/stdin-JSON), что именно-print;
   - требования к сложности или это не чистая задача по памяти/времени;
   - языки (заданные пользователем — ровно они, не «на усмотрение»);
   - тип тестов: unit-файл с функцией-тестами или stdin/stdout-кейсы
     (определяется драйвером runner'а выбранного языка).
3. **Черновик спецификации задачи** (statement + schema I/O) — показать
   человеку на согласование до кода.
4. **Генерация**: решение → тесты (каждый corner-кейс из чек-листа +
   базовые кейсы из примеров, нагрузочный опционально) → шаблоны.
5. **Harness-цикл**: прогнать решение против тестов; при падениях
   анализировать вывод, чинить решение/тесты — до стабильного зелёного
   на **всех** выбранных языках.
6. **Финализация**: показать диф-сводку файлов; после подтверждения —
   создать иерархию манифестов, записать файлы, перерегистрировать курс
   (`loadAndRegisterCourse` — уже существует), отрапортовать ссылки/путь.

## Структура файлов (существующий формат курса, ничего нового не изобретать)

```
<course>/
  course.yaml                        # slug, title, tracks
  tracks/<track>/track.yaml          # topics
  tracks/<track>/<topic>/topic.yaml  # units
  tracks/<track>/<topic>/<unit>/unit.yaml
  tracks/<track>/<topic>/<unit>/theory.md
  tracks/<track>/<topic>/<unit>/<task>/
    task.yaml                        # slug, title, statement, languages, difficulty?, tags?
    statement.md                     # Markdown: условие, примеры, ограничения
    go/  template.go  solution.go  solution_test.go
    python3/ ... cpp/ ...            # по одному каталогу на выбранный язык
```

- slug каталога =slug в манифесте (проверяет parser — жёсткое требование).
- Тесты — файлы, которые runner' драйвер уже умеет выполнять
  (`test_cmd` из `runners.json`); никакого нового формата тестов.

## Harness: черновой прогон без посылок (ключевая инфраструктура)

Инфраструктура runner'ов уже умеет исполнять код (см.
`internal/infrastructure/runner`, драйверы `run_cmd`/`test_cmd`, управляемые
Postgres-схемой для SQL-задач). Нужен «draft»-режим поверх неё:

- **Не создаёт Submission** в SQLite, **не пишет** прогресс, **не попадает** в
  историю «Посылок» UI, не помечает задачу решённой.
- Возвращает: статус (ok/broken/timeout), stdout/stderr, parsed-тесты
  (тот же `parseTestOutput`, что и в обычных посылках), длительность.
- Время ожидания и cleanup (tmp-dir для файлов черновика) — как в обычном
  runner'е; для SQL-драйвера — смет те же правила схемы.

### Новые MCP-инструменты (комплект авторинга)

- `list_courses_overview` — компактно: каталоги, курсы, топики, счётчики
  задач + подсказка, куда что класть (для шага размещения).
- `search_tasks` — из спеки поиска; тут используется для дедупликации.
- `draft_task_files { course, track, topic, unit?, task, languages[],
  statementMd, solution{lang}, tests{lang}, template{lang}, meta{tags[],difficulty} }` —
  **записывает только в staging** (draft-папка под data-dir, НЕ в courses).
  Возвращает структуру путей.
- `run_draft_tests { draftId, lang }` — гоняет черновой harness:
  тесты против решения/шаг-код. Не посылки, не прогресс (п. выше).
- `update_draft_files { draftId, files{...} }` — итеративные правки агента.
- `finalize_task { draftId, confirm: true }` — единственная точка записи
  в courses-dir: создание недостающих манифестов (`track/topic/unit`,
  если их нет), вставка slugs в родительские YAML (аккуратно: YAML
  комментари/формат сохраняем — правка вставкой строки списка), запись
  файлов задачи, перерегистрация курса, ответ — путь + серверный slug.
- `discard_draft { draftId }`.

ПравилаHarness-безопасности:
- draft-run исполняет решение агента — изолированно так же, как обычные
  посылки (tmp-dir, timeout, сеть запрещена как в обычном runner'е);
- запись в курсы — только через finalize после явного confirm человека;
- редактирование существующих задач через этот путь — отдельно► сначала
  финализация новых задач; изменение старых — будущая фаза (риск регрессии
  существующих студентов: обновление statement/тестов ломает прошлые сабмиты).

## Интеграция с AI

- Соединение через уже существующий `aiChatStream` (модель сконфигурирована
  в настройках) — те же провайдеры/ключи, никаких новых кредов.
- Промпт агента-автора — системная константа с протоколом пп. 1–6 и
  схемой файлов из этого документа.
- В UI AI Assist: кнопка «Создать задачу…» в панели ассистента — оверлей
  черновика (описание → вопросы → превью diff → финализация). Опциональная
  фаза: основное — MCP-путь, он же «агент с клавиатурой».

## Анти-требования (что не делаем)

- Не автоматически发布 без подтверждения.
- Не один全能-инструмент «создай задачуsetText» — разбиение на draft/iter/finalize,
  чтобы человек контролировал запись на диск и агент мог итерироваться.
- Не новые форматы тестов/манифестов — ровно те, что парсятся сегодня.
- Не запись посылок/прогресса в draft-прогонах (главный риск).

## Фазы

1. **Backend / MCP harness**: `run/execute вне посылок` (draft-run поверх
   runner), без UI. Тест: прогон решение→тесты без создания записей.
2. **Draft-хранилище + черновые манифесты** (staging, схемы, validate slug).
3. **MCP-инструменты авторинга** (draft, update, finalize, discard) и
   `search_tasks`-дедупликация.
4. **Финализация + перерегистрация** курса, e2e-сценарий «создать курс с
   нуля» и «добавить задачу в существующий топик».
5. (Опционально) **UI в AI Assist** — оверлей черновика.

## Критерии приёма

- Через MCP: «создай курс X и добавь туда задачу: <описание>» → агент задаёт
  минимум 3 уточняющих вопроса по corner-кейсам → генерирует решение/шаблоны/
  тесты для каждого указанного языка → harness-цикл доводит до зелёных →
  после подтверждения курс виден в UI, задача решается в редакторе, тесты
  проходят штатной посылкой.
- Заблокированная задача (падающий тест) не может быть финализирована:
  finalize возвращает список падающих тестов.
- В базе после draft-прогонов: посылок нет, прогресс не изменён.
- Существующие курсы не пострадали: перерегистрация проходит или откатывается.

## Риски / примечания

- YAML-файлы редактируются вставками (не перегенерацией) — иначе потеряются
  комментарии/форматирование рукопашных манифестов.
- Антивирус/Windows + частые tmp-прогоны — держать draft-run в тех же tmp-каталогах,
  что и обычные посылки, с тем же cleanup.
- Модель может сгенерировать невалидный Go/Python — draft-run это ловит; не
  публиковать код, который не прошёл harness (заменяет ревью человеком только
  частично: человек всё равно читает statement и решение перед confirm).

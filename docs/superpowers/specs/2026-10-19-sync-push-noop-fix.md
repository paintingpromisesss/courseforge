# GitHub-синхронизация: no-op push выполняется за пару секунд вместо ~2 минут

Дата: 2026-10-19
Статус: задача поставлена, реализация не начата
Область: `backend/internal/infrastructure/sync/sync.go`, `backend/internal/infrastructure/git/git.go` (только чтение API), тесты `sync_test.go`

## Симптом (наблюдение 2026-10-19)

Пользователь нажал «Отправить» в разделе «Облако» и получил «Отправка…»,
зависшую на ~2 минуты. За это время:

- `POST /api/sync/push` ответил `200` за **1м45с**;
- `last_sync` обновился на текущий момент;
- **нового коммита нет** — HEAD зеркала остался `87ba4f` (последний пуш 15.10),
  история не изменилась;
- рабочее дерево зеркала полностью чистое.

То есть пуш отработал корректно (no-op), но потратил ~105 секунд на
подготовку, в которой не было необходимости. С точки зрения пользователя
это выглядело как зависание.

## Диагноз

`Engine.Push` на каждое нажатие выполняет полный конвейер:

1. `snapshot`: `fetch` с origin → `checkout` ветки → **`wipeExceptGit`** (удаление
   всех файлов зеркала) → **копирование всего courses-контента заново**;
2. `CommitAll` — при чистом дереве это осознанный no-op («clean tree is a
   no-op, not an error»);
3. `Push` в origin — не вызывается (коммита нет).

Фактический объём зеркала на момент наблюдения: **13 653 файла / ~198 МБ**
(27 курсов, включая видео). Wipe+copy этих файлов занимает ~1м40с — Disk+AVG-скан
доминируют; сеть (fetch/push) почти не участвует.

Итог: самый частый сценарий «ничего не изменилось» оплачивает полную
пересборку снапшота.

## Фикс

Ранний выход (early exit) после снапшота: если снапшот не внёс изменений,
не делать `commit`/`push`, но зафиксировать успешную синхронизацию.

### Правки

1. **`sync.go`, `Engine.Push`** — после `e.snapshot(ctx, cfg)` добавить проверку:

   ```go
   // Snapshot идентичен HEAD (курсы не менялись с прошлого пуши) —
   // фиксировать нечего; фиксируем факт синхронизации и возвращаемся.
   if clean, err := e.git.IsClean(ctx, e.mirrorDir); err != nil {
       return fmt.Errorf("check mirror state: %w", err)
   } else if clean {
       cfg.LastSync = time.Now().UTC().Format(time.RFC3339)
       return e.cfgRepo.Save(ctx, cfg)
   }
   ```

2. **`git.go`, `Service`** — добавить публичный метод (вдохновлён паттерном
   `Dirty`, который уже используется):

   ```go
   // IsClean сообщает, совпадает ли рабочее дерево зеркала с HEAD
   // (те же критерии, что использует Dirty, но инвертированный вопрос,
   // чтобы не путать читателя намерением).
   func (s *Service) IsClean(ctx context.Context, dir string) (bool, error) {
       s.mu.Lock()
       defer s.mu.Unlock()
       out, err := s.runCmd(ctx, dir, s.timeout, "status", "--porcelain")
       if err != nil {
           return false, err
       }
       return strings.TrimSpace(out) == "", nil
   }
   ```

   Альтернатива без нового метода — переиспользовать существующий `Dirty`
   (инвертировать). Допустимо; новый метод предпочтительнее по читабельности
   вызова.

### Инварианты, которые фикс обязан сохранять

- Pull/restore-поведение не меняется: локальные курсы никогда не удаляются.
- `Push` по-прежнему никогда не делает force-push; retry-цикл
  (`lastErr → realign → retry`) остаётся как есть для ветки с изменениями.
- Сканирование исключений (`cfg.Exclude`) и игнорирование
  git-импортированных курсов (`sources.json`) — не трогается: они влияют на
  состав снапшота, а значит и на результат `IsClean`.
- `cfg.LastSync` обновляется и в no-op-случае: пользователь должен видеть,
  что проверка выполнена и актуальна. Это изменение UX-контракта по
  сравнению с текущим поведением (сейчас LastSync тоже обновляется — no-op
  уже сегодня проходит «успешно»), фикс его просто ускоряет.

### Что фикс НЕ делает

- Не добавляет инкрементальный снапшот (rsync-like copy) — отдельная,
  более крупная оптимизация; фикс не мешает ей в будущем.
- Не меняет UI: спиннер остаётся, просто завершается за секунды.
  Отдельной опцией можно показывать этапы (снапшот/коммит/пуш) — out of scope.

## Тесты

В `sync_test.go` есть инфраструктура локальных remote-репозиториев
(`TestPushPullRoundTrip`, `TestPushOverwritesRemoteSnapshot`):

1. **Ранний выход при no-op**: два вызова `Push` подряд с неизменившимся
   courses-каталогом. Ожидания: оба успешны; `git log` зеркала содержит
   один коммит (второй не создан); `config.LastSync` обновился после
   второго вызова; замер времени второго push — не обязателен, но
   уместен (не более N мс на CI — опционально, чтобы не флейкать).
2. **Изменение → коммит**: измене course-файла между двумя push'ами —
   второй создаёт коммит и реально пушит (существующий тест
   `TestPushOverwritesRemoteSnapshot` уже покрывает — не ломается).
3. **Exclude-каталог**: изменение внутри исключённого каталога → пуш
   остаётся no-op (снапшот не изменился).

## Критерии принятия

- Повторное нажатие «Отправить» без изменений курсов завершается < 2–3 с
  (fetch + checkout + пустой status), без нового коммита, `last_sync` свежий.
- Реальное изменение курса по-прежнему создаёт коммит и пушится
  (регресс-тесты зелёные).
- `git commit` и `git push` не выполняются при чистом снапшоте
  (проверяется тестом по логу зеркала).

## Оценка объёма

~30 строк кода (10 логики + 20 тестов), один файл синка + один метод git.
Риск низкий: механизм идемпотентен, существующие тесты на push/pull
выступают регрессионной сетью.

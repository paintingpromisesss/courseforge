# Поиск задач в CourseForge: от подстроки до AI-запросов

Дата: 2026-10-19
Статус: задача поставлена, реализация не начата
Область: фронтенд (глобальный поиск-оверлей), backend (endpoint поиска), MCP (инструмент `search_tasks`)

## Зачем

В CourseForge десятки курсов и сотни задач. Найти задачу сегодня можно только
навигацией по дереву. Нужен поиск, который работает **как в любом нормальном
приложении**: по вхождению слова в любом месте названия/тегов/текста, а не
по началу строки.

Ключевые сценарии:

- «пул» → все задачи, где «пул» встречается (Pool, Пул потоков, Пул соединений…);
- теги-горячие слова: у задач проставлены теги тем — пишешь `sync` → все задачи
  по синхронизации (теги `sync`, `synchronization`, …);
- человеческий запрос («найди задачу про блокировки в горутинах») → если
  AI-ассистент сконфигурирован, запрос уходит в модель, которая по базе задач
  определяет релевантные; результаты показываются в той же поисковой выдаче;
- тот же поиск — через MCP (агент ищет задачи курса программно).

## Правила сопоставления (договорённость, чтобы не спорить при реализации)

1. Запрос токенизируется по пробелам: `pool channels` = два слова.
2. Каждое слово ищется как **подстрока без учёта регистра** (`includes`),
   НЕ как префикс: «пул» матчит «Пул», «пул połączeń», «pull-based».
3. Логика между словами — AND (все слова должны найтись где-то в задаче:
   заголовок, теги, текст условия). Одно слово — один AND.
4. Теги: термин матчит и **весь тег как подстроку** (`sync` ⊂ `synchronization`).
5. Ранжирование результатов (сверху вниз):
   - точное совпадение слова с заголовком (word-boundary);
   - совпадение тега;
   - заголовок содержит слово;
   - только контент условия.
6. Лимит выдачи: 50 задач (`limit`, изменяемый), сортировка по рангу, потом по курсу.

## Backend

### `GET /api/search/tasks?q=&limit=&course=`

- Ищет по **загруженным** в память курсам (`h.courses`) — без IO по манифестам.
- Поля поиска фазы без контента: `task.title`, `unit.title`, `topic.title`,
  `track.title`, `course.title`, `task.tags[]`.
- Поля поиска по контенту: читает `statement.md` задачи (уже есть
  инфраструктура чтения unit-файлов; кэш карты `taskSlug → statement text`,
  инвалидация — при перезагрузке курса `revalidateGitContent`/`loadAndRegister*`).
  Контент — более тяжёлый проход, включается тем же `q`, ограничен по лимиту
  сниппетов (по ~120 символов вокруг первого совпадения).
- Ответ:

  ```json
  { "results": [{
      "course": "go-interview", "courseTitle": "…",
      "track": "неделя-4", "topic": "fan-in-fan-out", "unit": "01-fan-infan-out",
      "task": "golang-fanout-1", "title": "Fan-in для каналов",
      "tags": ["sync", "channels"], "difficulty": 2,
      "rank": "title",           // title-tag | title | tag | content
      "snippet": "…распределяется между несколькими goroutine…"
  }] }
  ```

- 400 на пустом `q` (< 2 символов), 503 если git… — нет: git тут не участвует.
- Учёт прогресса (done/not) в выдачу не включаем — клиент знает прогресс и может
  пометить иконкой.

## Фронтенд: поисковый оверлей

- Точку входа в шапку приложения (`App.tsx`): кнопка-лупа рядом с MCP-пилюлей +
  хоткей **Ctrl+K / Cmd+K** (Esc — закрыть, ↑/↓ — навигация, Enter — переход).
- Оверлей в command-palette-стиле поверх страницы: поле ввода, список
  результатов, футер с подсказками. Ленивая загрузка: список курсов подгружается
  при первом открытии; запрос с debounce 250 мс уходит в endpoint.
- Подсветка совпадений в заголовке и сниппете (`<mark>`, цвет `bg-warn/30` —
  нейтральный, не бренд-заливка).
- Сайд-информация в строке результата: курс → тема (крошкой), тег-бейджи
  (существующий `TagBadge`), сложность (существующий `DifficultyBadge`).
- Клик/Enter — переход на задачу существующим маршрутом (и оверлей закрывается);
  last-visit и прогресс не трогаются.
- Пустой запрос → вместо результатов: «Начните печатать…» + список тегов
  текущей библиотеки (клик по тегу = поиск по нему). Это и есть «горячие слова».
- Пустой результат → «Ничего не найдено по „…"» + предложение AI-режима
  (если он доступен), не заглушкой-пустышкой.

## AI-режим поиска (только при настроенном и включённом AI)

- Переключатель в оверлее: «обычный» / «умный» (иконка ✦). По умолчанию —
  обычный; кнопка появляется только если `aiConfig.enabled`.
- Запрос целиком (фраза пользователя) уходит в существующий поток
  `aiChatStream` с системным промптом: «Ты — поисковик по задачам CourseForge.
  Тебе дан список задач (слаг, заголовок, курс, теги). Верни JSON:
  {„task": slug, „score": 0..1, „reason": короткое пояснение} для ≤10 самых
  релевантных…» + **сжатый каталог задач** (слаг/заголовок/теги/курс, только
  метод алгоритмических задач ≤ 500 строк).
- Ответ парсится строго (JSON; при ошибке парсинга — молча откат на обычный
  поиск и надпись «AI недоступен, показан обычный поиск»).
- Результаты рендерятся теми же карточками + короткий `reason` под заголовком.
  Порядок — по score.
- Каталог для промпта собирается тем же backend (лёгкий вариант endpoint:
  `GET /api/search/catalog` → плоский список slug/курс/теги, без контента).
  Отдельный кэш на сервере — перечитывается при перезагрузке курсов.

## MCP: инструмент `search_tasks`

- Новый tool в MCP-сервере (там уже живут `get_current_task`, `list_courses`):
  `search_tasks { query: string, course?: string, limit?: number }`.
- Реинкарнация того же backend-поиска (та же функция, не дубликат логики).
- Ответ — тот же JSON, что у endpoint (слаг, заголовок, путь, теги, сниппет) —
  агент может сам выбрать задачу и затем вызвать `set_active_task`.
- Описание tool для агента: «Поиск задач по словам, тегам и контенту условий.
  Примеры: query=„пул“, query=„mutex timeout“, query=„sync“».

## Фазы (порядок реализации)

1. **Backend-поиск** (`/api/search/tasks`): подстроки по названию/тегам/путь +
   ранжирование + лимиты. Без контента. Тесты: substring/регистр/теги/AND.
2. **Оверлей Ctrl+K** на фронте: поле, карточки, клавиатура, переходы,
   hot-tags, подсветка.
3. **Поиск по контенту условий** (backend): чтение statement.md с кэшем +
   сниппеты; в оверлее — расширенные совпадения.
4. **AI-режим**: `/api/search/catalog` + системный промпт + parse/fallback.
5. **MCP `search_tasks`**: тот же сервис, минимальная обвязка tool-описания.

Фазы 1–2 — MVP (можно проверять/использовать), 3–5 — независимо друг от друга.

## Не в scope

- Морфология/стемминг («каналов» не найдёт «канал») — v1 честный substring;
  при необходимости позже — нормализация форм через дополнительный индекс.
- Полнотекстовый индекс (SQLite FTS / Bleve) — массивы задач скромные
  (сотни), линейный скан по памяти быстрее любoго индекса.
- Поиск по теории/материалам вне условий задач, поиск по UI-разделам.
- История запросов и «недавние» — можно потом (localStorage тривиален).

## Критерии приёма

- «пул» находит задачи со словом «пул» **внутри** заголовка/условия, а не
  только с префикса;
- тег `sync` находится по запросу «sync» и группируется выше обычных совпадений;
- Ctrl+K открывает поиск с любой страницы, Enter ведёт на задачу, Esc закрывает;
- при включённом AI фраза «что у меня по мьютексам» возвращает задачи
  с пояснением; при выключенном AI AI-переключатель скрыт;
- MCP-агент вызывает `search_tasks` и получает тот же результат, что и UI;
- бэкенд-тесты на matching/ранжирование/лимиты зелёные.
